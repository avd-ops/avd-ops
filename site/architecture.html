How the AVD repos fit together

Three repos are the foundation: what it is, what it should be, and how we build it across five control planes. Two more sit on top and automate it, so it gets smarter over time. Every diagram on this page can be downloaded as SVG, Mermaid or Draw.io for architecture reviews and decision records.

The layers

Read it from the bottom up. Three repos are the foundation, orchestrating five control planes. The layer on top automates it and makes it smarter over time.

Front door

avd-ops: where to start. The map of the repos, what each one does and how they connect. Each repo stays the source of truth for itself.

On top: Desktop DevOps across AVD, Windows 365 and Intune (optional)

Makes it smart: avd-second-brain

Desktop DevOps intelligence and memory across AVD, Windows 365 and Intune: remembers why the estate is the way it is and learns from every change. It thinks; it never holds a write credential.

Automates it: avd-swarm

Desktop DevOps agents across AVD, Windows 365 and Intune. They read freely, detect drift and change nothing until a person approves the exact plan, with one kill switch only the owner resets. The avd-buddy chat lives here.

The top layer builds on the foundation. The foundation never needs it.

Foundation

What it is: avd-current-state

Read-only collection and validation across all five control planes, offline: what is in the environment today, and whether a deployment landed correctly.

What it should be: avd-assess

The target, and why: a research index that links out to Microsoft's published guidance, pinned, and writes new method only for a gap.

How we build it: avd-landing-zone

Builds the landing zone in Bicep and orchestrates the five control planes through the portal-guided Cloud Shell flow, with preflight checks, cleanup and same-tenant DR.

What it is and How we build it work on their own, with no brain and no swarm. avd-linecheck measures end-user browser reachability and round-trip latency.

1. Logical architecture and contract flows

The repos don't share code. They pass versioned contracts and pinned control-plane handoff manifests. Solid arrows are the family's own paths; dashed ones are optional.

2. Network, subnet and Private Link topology

The Azure landing zone deploys a segmented 10.100.0.0/22 virtual network across six resource groups. Session hosts have no public IP addresses; storage, Key Vault and AVD control-plane traffic stays on Private Endpoints in 10.100.2.0/27.

3. Session, identity and storage traffic flows

Session hosts accept zero inbound connections from the internet. User sessions establish outbound Reverse Connect TLS channels to the AVD gateway (plus UDP 3478 STUN/TURN for RDP Shortpath), while FSLogix profile mounts stay over SMB 445 to the storage Private Endpoint authenticated with Microsoft Entra Kerberos.

4. Bicep deployment dependency graph (DAG)

In bicep/main.bicep, module dependencies come from explicit outputs so Azure Resource Manager sequences prerequisite stages and parallelizes independent ones.
