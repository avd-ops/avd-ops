Security review

What a security reviewer needs, in one map.

Approving an Azure Virtual Desktop deployment built with the avd-ops repos? This page lists what each repo does for security, links the file that does it or proves it at a pinned commit, and says how strong that proof is, what you still own, and what is missing.

It is a map, not a copy and not an audit: every line points at the repo that holds the detail. The map itself lives in avd-assess (security-review.yaml), and this page renders it at commit cfcc302, checked 2026-10-27. Nothing here is a security audit, a compliance attestation or a penetration test.

How strong the evidence is

Each claim carries one standing, the strongest its evidence supports. Of 44 claims: 3 run, 26 guarded, 11 built, 4 designed.

Run
A real run showed it: a lesson or a run record is in the evidence.
Guarded
A check in CI fails if it breaks.
Built
It is in the code; no test or real run was found for it.
Designed
Written down only: a spec or a proposed decision, not built or not run.

The reviewer's questions

Each question is answered by the claims and the operator decisions it links.

  1. Which identities deploy, read and change the estate, with which roles and for how long? lz-deploy-owner, lz-ci-oidc, lz-graph-delegated, lz-rbac, entra-ca-groups, cs-reader-only, cs-graph-readonly, swarm-identities, op-subscription-owner
  2. Where is every secret, who can read it, and does any operator have to remember or paste one? lz-break-glass, lz-key-vault, lz-jumpbox, lz-ci-oidc, lz-registration-token
  3. What is reachable from the internet, and how do admins reach hosts? lz-private-link, lz-private-data-plane, lz-nsg, azure-plane-network, pp-vnet-enterprise-policy, lz-jumpbox
  4. How are user profiles authenticated, encrypted and protected from deletion? lz-profile-share, op-ntfs, lz-last-copy
  5. How are hosts hardened, checked for drift and protected? lz-trusted-launch, lz-encryption-at-host, lz-host-baseline, lz-defender-intune, intune-host-profiles, m365-vdi-baseline, op-trust-boundary, op-host-baseline, op-endpoint-protection
  6. What can move between the user's device and the session? lz-redirection, op-redirection
  7. Which Conditional Access, MFA and consent decisions does the deployment need from the tenant? entra-ca-groups, op-conditional-access, op-admin-consent
  8. Which guardrails, logs and budgets are on, and which come from the platform? lz-policy, lz-budget-shutdown, pp-dlp-baseline, op-platform-policy, op-logging
  9. What do the tools collect, where does it go, and what leaves the browser or the tenant? cs-reader-only, cs-graph-readonly, cs-facts-redaction, cs-portal-state, lz-portal-local, lz-portal-report, brain-layers, family-no-ids, op-pseudonym-key
  10. Can the code and its dependencies change under a passing build? lz-pinned-tools, lz-psrule, secret-scan, lz-actions-pinned, pinned-sources, family-licenses
  11. Can any automation change the estate without a person's approval? brain-no-write, swarm-gate, swarm-prompt-shields, op-environment-reviewers

What each repo can touch

A short summary per repo, not a formal threat model. A formal review exists for avd-swarm; the others have none yet.

avd-landing-zone

Orchestrates the five control planes and creates and changes every resource in the landing zone subscription, the groups and apps it needs in Entra, and deletes on teardown.

Risks: An over-privileged deploying identity; A secret in the repo or a log; Public exposure of data services; A teardown that deletes the only copy.

Limited by: lz-deploy-owner, lz-ci-oidc, lz-break-glass, lz-private-data-plane, secret-scan, lz-last-copy

No formal threat model yet.

avd-entra

Creates and configures AVD Entra dynamic groups, Conditional Access policies, and the Kerberos storage principal in the Entra plane.

Risks: A Conditional Access change locking out administrators; Over-broad Graph write scopes during deployment.

Limited by: lz-graph-delegated, op-conditional-access, op-admin-consent

No formal threat model yet.

avd-intune

Deploys Intune Settings Catalog profiles, compliance policies, and security baselines for AVD session hosts.

Risks: Misconfigured device policy affecting non-AVD endpoints.

Limited by: lz-defender-intune, op-host-baseline

No formal threat model yet.

avd-m365

Configures OneDrive Known Folder Move, Microsoft 365 Apps Shared Computer Activation, Teams media optimization, and multimedia redirection policies.

Risks: Unintended tenant-wide collaboration policy scope.

Limited by: lz-graph-delegated, op-admin-consent

No formal threat model yet.

avd-azure

Deploys the Azure Resource Manager plane (networking, storage, Key Vault, host pools, session hosts, monitoring, and policy guardrails).

Risks: Public exposure of storage or Key Vault; Over-privileged role assignments.

Limited by: lz-private-data-plane, lz-rbac, lz-policy

No formal threat model yet.

avd-power-platform

Configures Power Platform environments, Data Loss Prevention connector policies, and VNet enterprise policies when opted in.

Risks: Unblocked connectors exfiltrating data from session hosts.

Limited by: lz-policy, op-platform-policy

No formal threat model yet.

avd-current-state

Reads the subscriptions and control planes it is pointed at; writes only local files.

Risks: A read identity granted more than Reader or read-only Graph scopes; Collected names or IDs leaving with the facts.

Limited by: cs-reader-only, cs-graph-readonly, cs-facts-redaction, cs-portal-state

No formal threat model yet.

avd-assess

Nothing in Azure; publishes method, references and contracts that the other repos pin.

Risks: A changed contract or rule reaching readers unreviewed.

Limited by: pinned-sources

No formal threat model yet.

avd-second-brain

Reads redacted facts and knowledge; holds no write credential.

Risks: Estate data reaching public knowledge.

Limited by: brain-layers, brain-no-write

No formal threat model yet.

avd-swarm

In design, the only write path for the layers above the foundation.

Risks: An unapproved write; A fooled agent proposing a bad plan; Prompt injection through tool output.

Limited by: swarm-gate, swarm-identities, swarm-prompt-shields

Red team review

avd-ops

The static site; no Azure access.

Risks: Private material published by mistake.

Limited by: family-no-ids, secret-scan

No formal threat model yet.

Reporting a vulnerability

Privately, through Report a vulnerability on the affected repo's Security tab. Where a repo has no security policy yet (avd-landing-zone, avd-current-state, avd-second-brain, avd-swarm) and the button isn't there, open an issue that asks for a private contact and holds no details. Never put secrets, IDs, names or estate data in a public issue.
