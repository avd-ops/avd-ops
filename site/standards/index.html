Standards library

Edition a5a7eee of avd-assess, 2026-10-21. What changed

What an Azure Virtual Desktop estate should be, and why: the avd-assess methods, each step citing a pinned published source, our own observation, or method we wrote where no source exists.

This is a reading view of avd-assess, which holds the standards; the pages here add nothing of their own. 248 sources, 1037 claims, 37 observations, 42 gaps and 10 checks in this edition.

Methods

  • Assessment methodHow to judge what was collected against published recommendations. avd-current-state implements this method and writes the report (avd-second-brain contract C21).
  • Baseline profile: what good looks likeWhat a healthy AVD host pool looks like, as numbers: the experience users should get, the utilization a host should run at, and the density and size to start from, each with its source and standing. Targets and benchmarks lists the numbers one by one; this method puts them together into one profile per workload class, in baselines.yaml, so an estate can be judged and tuned against it. Most of the assembly is ours.
  • Collection methodWhat to collect about an AVD estate, from where, and how private each fact is. avd-current-state implements this method; the facts it writes are avd-second-brain's contract C11, named by the fact register (C15).
  • FinOps methodHow to judge what an estate costs, and whether it costs what it should, against what Microsoft and the FinOps Foundation publish. It is the assessment method applied to the cost pillar, with the extra sources cost needs. avd-current-state implements it; the findings go in the same report (contract C21). Nothing here is a bill, a quote or financial advice.
  • Intune and host management methodHow to judge the way an estate manages its session hosts and the client devices that reach them: Intune for hosts and devices, against Group Policy where an estate keeps it. It is the assessment method applied to the Intune and host management pillar (intune in dimensions.yaml). Microsoft documents what Intune supports on AVD hosts, so the method links out to those pages and adds only the scope page: which state to read, how devices map to pools, and which limits make a setting not applicable rather than missing.
  • Network methodHow to judge an estate's network, Azure side and client side, against what Microsoft publishes for AVD. It is the assessment method applied to the network, and it is a map: each step points at the pinned source, the fact that measures it and the check that judges it, and says so plainly where none exists. Nothing here restates Microsoft's lists; read them at the pin. avd-current-state implements it; findings go in the same report (contract C21). The rows are network.* in dimensions.yaml.
  • Reliability methodHow to judge whether an estate stays available through a host or zone failure and comes back after a region loss, a deletion or a bad change, against what Microsoft publishes for AVD. It is the assessment method applied to reliability, availability zones, backup, business continuity and disaster recovery, and it is a map: each step points at the pinned source, the fact that measures it and the check that judges it, and says so where none exists. Nothing here restates Microsoft's guides; read them at the pin. The rows are reliability.*, profile.backup and profile.cross-region in dimensions.yaml; the review checklist's A01 to A03 items are all on a row.
  • Remediation methodHow to turn reviewed findings into an ordered plan of changes. This is the fifth stage of an assessment, after collection, discovery, analysis and review. avd-current-state's assessment portal writes the plan (contract C24, avd-remediation-plan/v1) from the assessment report (C21), its review (C23) and the hints in method.json. avd-landing-zone makes the changes; nothing here needs a layer above it.
  • Remote protocol and session methodHow to judge the way users' sessions reach their hosts: which transport RDP uses and why, what keeps a session alive when a path fails, and the session settings that ride on the transport (redirection, graphics, Teams and media, time limits). It is the assessment method applied to the remote protocol and session pillar (protocol in dimensions.yaml). Almost all of it is documented by Microsoft, so the method links out to those pages and adds only the transport map and the scope page. The networking pillars own how the network provides what RDP needs; this page states what it needs.
  • Sample check methodA short, point-in-time health check of an estate's measured user experience: a few chosen hours, judged against thresholds that each carry their source, before anyone changes anything. It sits between the assessment, which judges configuration, and the targets and benchmarks, which say what good looks like. No open method covers it, so most of it is ours.
  • Scoring methodHow check outcomes roll up, and which target-state decisions the evidence can support. No open standard exists, so this method is ours and labeled as a hypothesis.
  • Security methodHow to judge an estate's security against what Microsoft publishes for AVD. It is the assessment method applied to the security pillar, with the extra sources security needs. avd-current-state implements it; the findings go in the same report (avd-second-brain contract C21). Nothing here is a security audit or a compliance attestation.
  • Targets and benchmarksWhat good looks like, as numbers with their sources. A benchmark is published (a source states it), prior (a source states it but calls it an estimate) or baseline (no source has a number, so the estate's own measurement sets it).
  • Troubleshooting and diagnostics methodHow to find out why something is wrong in an AVD estate: which source answers which symptom, in what order to read them, and what stays unknown. It is the assessment method applied to the troubleshooting and diagnostics pillar (diagnostics in dimensions.yaml). It is the one pillar that is a flow rather than a list of settings, so it needs this page. Microsoft documents each component's troubleshooting; the method links to those pages and adds only the map that joins them: the data sources, the error-code map and one triage flow per symptom. The monitoring pillar says the data must exist; this page says how to read it when something is wrong.
  • Tune and rightsizeA repeatable loop for making a running AVD estate perform as its baseline profile says, at the lowest cost that keeps it there: measure, compare, change one thing, measure again, record. avd-assess holds the loop; avd-landing-zone applies each change; avd-current-state measures before and after. The order of levers and the record are ours.
  • Use case methodWho uses the estate, for what, and what that means it should be. Collection says what is there and assessment judges it against published guidance; this method supplies the other half of "should be": the personas, their apps, their performance and experience needs, and their security and compliance needs. It is the analysis side of discovery, the second stage of an assessment. avd-current-state checks a use case record against what it collects; nothing here needs a layer above it.

How far each claim is proven

Every claim carries three marks. Of 1037 claims, 1037 are mapped, 15 measurable and 22 validated; 14 are waiting on a run that tests them.

✓ mapped○ measurable○ validated
A pinned source states it.
✓ measurable
A check in method.json reads it, and every fact the check needs is collected today.
✓ validated
An observation from a real run, with public evidence, agrees with it or extends it.
