Baseline profile: what good looks like

methods/baseline-profile.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

What a healthy AVD host pool looks like, as numbers: the experience users should get, the utilization a host should run at, and the density and size to start from, each with its source and standing. Targets and benchmarks lists the numbers one by one; this method puts them together into one profile per workload class, in baselines.yaml, so an estate can be judged and tuned against it. Most of the assembly is ours ([G1]).

Method

  1. Set targets as numbers before measuring anything, one per experience metric, tied to the workload ([1, PE:01], [2, measurable-targets]).
  2. Give each host pool a workload class, light, medium, heavy or power, from its persona record in the use case method, or from the sizing guide's examples when there is none ([3, multisession-users-per-vcpu], [3, estimates-only], [G1]).
  3. Start from the class's profile: the common experience targets and utilization bands plus the class's density and minimum size ([G1]). A persona may tighten a value, never loosen it without a recorded reason.
  4. Treat experience as a gate: round-trip time ([4, rtt-under-150]), input delay per session and per host ([5, input-delay-bands], [6, input-delay-host-100], [3, input-delay-expectation]), and logon and app load time as the estate's own baseline ([G2]).
  5. Treat utilization as bands, under, good, watch and over, for CPU and memory per host in working hours ([7, user-facing-targets], [8, cpu-bands], [8, pql-per-processor]). Both over- and under-provisioning are findings ([9, over-and-under]).
  6. Measure the same way every time: at least seven days, the ramp-up and peak hours from intake, percentiles rather than averages ([7, lookback], [2, percentiles], [G3]).
  7. Keep density inside the published range and start at or under the class prior: multi-session hosts of 6 to 24 vCPU, more smaller hosts, two or more per pool and headroom for sign-in storms ([3, multisession-vcpu-range], [3, more-smaller-vms], [3, logon-storm-headroom]).
  8. Replace priors with the estate's own measurement: the first full window becomes the estate's baseline ([10, baseline-defined], [10, record-baselines]), and the measured density replaces the class prior ([O1]). Results come back through one evidence intake that the public and we both use ([G4]).
  9. Show the deviation thresholds next to every result, so a reader sees how far from the profile is acceptable ([9, deviation-thresholds]).
  10. Refresh the profile before a predicted change in use (a new team, a new app, a season) and on the assessment cadence ([1, PE:02], [11, milestones]).

Where it fits

Repo Its part
avd-assess The profile and its sources (baselines.yaml)
avd-landing-zone Deploys a new host pool at or inside the class's profile: size, session limit, host count
avd-current-state Measures the estate and judges each host pool against its profile

The tune and rightsize method is how a running estate moves toward its profile.

Not yet known

  • No profile value has been checked against users we measured; every density is still the sizing guide's estimate ([O1]).
  • Memory per user, users per GPU, disk latency and a memory ceiling for a session host have no published number ([G1], [G5]).

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]not yet tested users-per-vcpu-adopted, on session-host-sizing#multisession-users-per-vcpu, 2026-10-20. Adopted as the landing zone's automatic sizing input, and its preflight warns above 6 sessions per vCPU. No real users have been measured against it, so the numbers are still Microsoft's prior, not our evidence.
