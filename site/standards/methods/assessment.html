Assessment method

methods/assessment.md · Edition a5a7eee of avd-assess, 2026-10-21. What changed

How to judge what was collected against published recommendations. avd-current-state implements this method and writes the report (avd-second-brain contract C21).

Microsoft starting point

Microsoft publishes no single AVD assessment standard, so the method starts from three public sources, each for one job (the numbers a healthy estate should hit are the separate baseline profile):

  • Scope (what an assessment must answer): the Cloud Adoption Framework's AVD assessment questions ([1]). Microsoft is retiring that page; the pin keeps it.
  • Items (what to check, with short IDs, pillar and severity): the AVD review checklist ([2]), with APRL through WARA for reliability ([3], [4]).
  • Questionnaire (the design-choice self-assessment): the Well-Architected Review, core plus the AVD workload review ([5, avd-workload-review]).

Everything else here builds on those three: evidence mapped to items, measured targets, scoring and our own observations.

Method

  1. Start from Microsoft's lists, not ours: the AVD review checklist for all pillars ([2]) and APRL through WARA for reliability ([3], [4, collector-avd-json]). Where PSRule for Azure, which avd-landing-zone runs on its templates, has a rule for the same item, cite its rule ID beside the item so both name one thing ([6], [G1]).
  2. Map each item to the facts that decide it, and leave the rest unknown with the data they would need ([G1]).
  3. Give each check one of four outcomes: pass, warn (a trade-off to review), gap, or unknown. Unknown is never guessed, and a model never decides an outcome ([G2]).
  4. Judge the image against the landing zone's reviewed WDOT profile, not against every WDOT item: some items destroy evidence or break sysprep ([7, categories], [O1], [O2]).
  5. Use the Well-Architected checklists' codes (RE:04 and the rest) to place each finding in its pillar ([8, RE:04]).
  6. Judge the security pillar with the security method, which adds the sources security needs ([9], [G3]).
  7. Judge transport and session settings with the remote protocol and session method, which maps the transport vocabularies and judges each connection against the networks users connect from ([G4], [G5]).
  8. Judge host and device management with the Intune and host management method, which reads Intune state per host pool and scores what multi-session can't receive as not applicable ([G6]).
  9. When something is wrong, find the cause with the troubleshooting and diagnostics method, which maps each symptom to the sources that explain it and the pillar that owns the fix ([G7], [G8]).
  10. Repeat on a cadence and compare to the last run, as the Well-Architected Review does with milestones ([5, milestones]).

Not yet known

  • Most checklist items aren't mapped yet; version 1 maps a handful ([G1]).
  • Whether our outcomes agree with the Well-Architected Review's own answers for the same estate has not been tested ([5, questionnaire]).

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]extends wdot-disk-cleanup-deletes-evidence, on vdi-optimization-guide#test-cleanup-first, 2026-10-20. WDOT's DiskCleanup category deletes every log, trace and event log file on the system drive, including an image build's own evidence before the image test reads it. The landing zone keeps that category off and cleans narrowly instead.
  2. [O2]agrees wdot-appx-removal-left-off, on vdi-optimization-guide#sysprep-store-apps, 2026-10-20. The landing zone's image build keeps WDOT's Appx package removal off for this reason; no sysprep failure has been seen with it off. Not yet tested with it on.

Our own method (gaps)

Where no published source covers a step, avd-assess writes the method and says what was searched and not found.

  1. [G1]checklist-mapping: mapping facts to review checklist items.
  2. [G2]scoring: scoring.
  3. [G3]security-scope: what a security assessment covers, and which repo does what.
  4. [G4]remote-protocols-scope: what a remote protocol and session assessment can judge, and from where.
  5. [G5]transport-classification: one name for the transport a connection used.
  6. [G6]intune-scope: what an Intune and host management assessment can judge, and from where.
  7. [G7]diagnostics-scope: what a troubleshooting and diagnostics assessment can read, and which part becomes a fact.
  8. [G8]error-code-map: one map from the code an operator sees to its meaning and its flow.
