Desktop DevOps method

methods/desktop-devops.md · Edition 004394b of avd-assess, 2026-11-08. What changed

How to apply DevOps -- versioned infrastructure and policy-as-code, offline read-only sensing, deterministic standards checks, and gate-checked remediation -- across Azure Virtual Desktop (avd), Windows 365 Cloud PCs (win365) and Microsoft Intune (intune). The full architectural writeup and traceability matrix are in docs/desktop-devops.md.

Method

  1. Scope the desktop platforms in intake before evaluating checks: record intake.avdScope (pooled, personal, both, not-used) and intake.win365Scope (not-used, enterprise, frontline, both) alongside the user personas (use-cases.yaml) so checks for unused platforms evaluate to not-applicable rather than false gaps ([G1], [G2], [G3]).
  2. Version all five control planes as code in Git: define AVD compute, storage and networking in Bicep (avd-azure), Entra groups and Conditional Access covering both AVD and Windows 365 application IDs (avd-entra), Intune Settings Catalog profiles, compliance policies, platform assignment filters and Windows 365 provisioning policies and user settings as Graph JSON (avd-intune), Microsoft 365 shared activation and OneDrive/Teams VDI policies (avd-m365), and Power Platform DLP boundaries (avd-power-platform) ([G4], [G2]).
  3. Isolate desktop platforms with Intune assignment filters: deploy explicit assignment filters for multi-session AVD hosts (device.osSku -eq "ServerRdsh"), personal AVD hosts, Windows 365 Cloud PCs (device.model -startsWith "Cloud PC") and physical workstations, and verify that no workstation-only policy targets All Devices without a filter ([1, assignment-filters-separate-platforms], [2, settings-catalog-only], [G5]).
  4. Collect live state read-only and redact offline into contract C11: read Azure Resource Graph, Entra ID, Intune and Windows 365 (deviceManagement/virtualEndpoint) without write permissions, and emit a zero-PII avd-current-state-facts/v1 snapshot whose fields map to registered C15 fact IDs ([G6], [G5], [G2]).
  5. Evaluate multi-session AVD and Windows 365 Cloud PC baselines deterministically: run method.json against the C11 snapshot and C19 intake to check Intune secure-by-default compliance (asm-intune-no-policy-noncompliant), FSLogix, RDP Shortpath and session limits (asm-intune-fslogix-configured, asm-intune-shortpath-configured, asm-intune-session-limits-configured), absence of update rings on multi-session pools (asm-intune-no-multisession-update-ring), and -- when Windows 365 is in scope -- provisioning policy SSO (asm-win365-sso-enabled), no persistent local administrator (asm-win365-no-local-admin), restore-point frequency within 24 hours (asm-win365-restore-points-24h), Azure Network Connection health (asm-win365-anc-healthy) and Cloud PC device compliance (asm-win365-cloudpcs-compliant) ([1, provisioning-policy-sso], [1, user-settings-least-privilege], [1, restore-point-cadence], [1, anc-health-checks], [1, cloudpc-intune-compliance]).
  6. Evaluate consumption and license FinOps side by side: check AVD hourly compute and storage utilization (autoscale, Start VM on Connect, right-sizing against C12 concurrency) alongside Windows 365 step-function license utilization (c11.entra.skuWin365Available and provisioned Cloud PCs with zero connections) ([3, CO:05], [4, E01.05], [G7], [G2]).
  7. Route fleet policy drift to GitOps pull requests and tactical host or Cloud PC actions to gate-checked plans: propose Intune Settings Catalog, compliance and assignment filter fixes as policy-as-code pull requests (desktopDevOpsAction: policy-pr against avd-intune), and require every destructive runtime action (reprovision, deprovision, replace-session-host) to pass the governance gate's session-drain preconditions and D1 data-loss guard (restorePointVerified: true with restorePointAgeHours <= 24, or discardLastCopyApproved: true) before a human approves in the GitHub Environment ([2, remote-actions-unsupported], [1, restore-point-cadence], [G8], [G2]).

Not yet known

  • Whether Microsoft Graph's deviceManagement/virtualEndpoint/cloudPCs connection-quality and last-sign-in reports expose sufficient granularity across both Enterprise and Frontline Cloud PCs without requiring Log Analytics or an endpoint agent ([G2], [G5]).
  • How quickly Intune assignment filter evaluation converges when a session host or Cloud PC is reprovisioned under an existing device name ([O1], [G5]).

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]agrees device-records-outlive-hosts, on intune-avd-multisession#orphaned-records, 2026-10-21. Deleting the landing zone's demo hosts left their Entra ID and Intune device records behind until the cleanup script deleted them through Graph; a cleanup whose Graph sign-in timed out couldn't find the names on a second run until the fix kept the deployment record. Anything that recreates hosts (session host update, a rebuild) leaves the same records unless a step removes them.
