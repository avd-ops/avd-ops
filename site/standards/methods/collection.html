Collection method

methods/collection.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

What to collect about an AVD estate, from where, and how private each fact is. avd-current-state implements this method; the facts it writes are avd-second-brain's contract C11, named by the fact register (C15).

Method

  1. Read the control plane with Reader only, through Azure Resource Graph where it has the property, one query per resource type, and REST where it doesn't. Cmdlets that reshape output are a last resort. APRL's AVD queries show the Resource Graph shapes for host pools and scaling plans ([1]). Host pools are in the Resources table and only session hosts in DesktopVirtualizationResources ([2, dv-table-session-hosts]); each fact's table, type and property is in method.json ([G1]).
  2. Run WARA's collector for reliability (Start-WARACollector -AVD) and keep its JSON, not its Excel or PowerPoint ([3, collector-avd-json], [3, report-needs-windows]). It covers Reliability only ([3, reliability-only]), so the other pillars come from step 1.
  3. Redact before anything leaves the operator's session. Facts are counts, booleans, public Azure values and keyed pseudonyms, with no names, IDs, addresses or free text. Each fact's privacy class is in the register ([G2] lists the facts the checks need).
  4. Ask the intake questions that telemetry can't answer ([G3]), and the discovery questions about who uses the estate for what ([G4], use case method).
  5. Measure latency where the user is, from the user's device against regional endpoints, never from Cloud Shell ([O1], [4, rtt-under-150]).
  6. For measured use, read the AVD Insights data the estate already collects (time to connect by stage, round-trip time, input delay, the recommended performance counters) over a stated window, read-only, with Log Analytics Reader ([5, time-to-connect-stages], [6, counter-set], [7, reader-roles]). Take each measure's query from the Insights workbooks rather than writing a new one ([8, queries-define-measures]). Reading existing Insights data is in scope; turning on new collection in an estate is a change, made by whoever runs it. The measured facts and their open questions are in [G5].
  7. Don't build a general inventory; wrap ARI for it. For a full inventory and a network diagram, use ARI as an opt-in step ([9, excel-inventory]). Its diagram draws from the Resource Graph rows it is given ([9, diagram-from-rows]), so the rows are redacted before it draws, keeping each ID's shape. An AVD overlay and stable IDs are our additions. The collector, the validator and the C11 facts never require ARI.

Not yet known

  • Which checklist items need facts the collector doesn't read yet: the profile storage region ([G2]), and the monitoring configuration per AVD object and host ([G5]).
  • Image optimization state inside the guest isn't visible from the control plane ([10, categories]). What is visible is the WDOT pin and profile an image version records, when its build tagged it ([O2]); an untagged image's state stays unknown, not failed.

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]extends region-latency-from-the-user, on avd-prerequisites#rtt-under-150, 2026-10-20. Latency measured from Cloud Shell says nothing about users, because Cloud Shell runs in an Azure datacenter. Measure round-trip time from the user's device, against endpoints verified to be regional.
  2. [O2]extends wdot-pin-on-image-version, on wdot#optimization-state, 2026-10-20. What runs inside the guest isn't visible from the control plane, but the landing zone's image build tags each gallery image version with the WDOT release, commit and profile hash it ran, so a Reader can see which pin and profile an image claims. Images built any other way carry no such record.
