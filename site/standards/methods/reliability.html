Reliability method

methods/reliability.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

How to judge whether an estate stays available through a host or zone failure and comes back after a region loss, a deletion or a bad change, against what Microsoft publishes for AVD. It is the assessment method applied to reliability, availability zones, backup, business continuity and disaster recovery, and it is a map: each step points at the pinned source, the fact that measures it and the check that judges it, and says so where none exists. Nothing here restates Microsoft's guides; read them at the pin. The rows are reliability.*, profile.backup and profile.cross-region in dimensions.yaml; the review checklist's A01 to A03 items are all on a row.

AVD has no disaster recovery of its own ([1, no-native-dr]). Microsoft runs and fails over the control plane ([2, control-plane-microsoft]); the hosts, profiles, apps, user data and identities are the customer's ([1, customer-managed-components]). The method judges only the customer's part.

Method

  1. Targets first. Each workload's RTO, RPO and expected availability come from the business, not from the platform: the AVD service has no financially backed SLA ([3, A01.01], [4, RE:04], [5, no-financial-sla]). Intake intake.recoveryTime and intake.recoveryPoint, for the strictest workload while intake is per estate; without them every later step can only describe, not judge. Row reliability.targets.
  2. Critical workloads in their own pools, so each pool can take the recovery model its targets need ([3, A01.03], [5, separate-critical-apps]). The use case record names them (use cases). Row reliability.critical-pools.
  3. Zones for availability, with hosts to spare for a lost zone, fixed when the VMs are created ([3, A01.04], [6, spread-and-overprovision], [5, availability-option-at-create]). Zones are not disaster recovery ([6, zones-not-dr]). Row reliability.zones.
  4. A recovery model per pool for a region loss: rebuild, restore, warm standby (active-passive) or active-active, chosen from the targets and intake.regionRecovery ([3, A01.02], [6, active-active-vs-passive]). Microsoft's RTO and RPO per model are estimates ([6, rto-rpo-by-model], [6, estimates-to-test]); recovery-region capacity is guaranteed only for running VMs or a reservation ([6, capacity-not-guaranteed], [7, reserves-capacity]); standby hosts start every 90 days ([6, token-refresh-90-days]). Row reliability.dr-model.
  5. Personal pools hold state: Site Recovery per VM, to another zone or region, never its test failover on session hosts ([3, A01.06], [6, personal-site-recovery], [6, no-asr-test-failover], [8, may-fall-short-region-wide]). Row reliability.personal-hosts.
  6. No VM backup for pooled hosts; they are rebuilt from the image ([3, A01.05], [5, hosts-stateless-no-vm-backup]). Row reliability.host-backup.
  7. The image is where the pool will be rebuilt: each version replicated to both regions on zone-redundant storage, and a gallery in each region ([3, A02.01], [9, not-global], [9, zrs-in-zone-regions]). Row reliability.image-regions.
  8. Dependencies come too: domain controllers with DNS, sync staging, hub and hybrid links, line-of-business apps, app packages per region and a log workspace that survives; the directory's configuration exported as a known-good state ([3, A02.02], [5, dependencies-in-recovery-region], [6, identity-in-recovery-region], [6, msix-account-per-region], [6, log-workspace-per-region], [10, document-known-good]). Intake intake.recoveryDependencies; most of it is outside what a Reader can see. Row reliability.dependencies.
  9. Decide what profile data matters before protecting it ([3, A03.01], [5, assess-what-to-protect], [6, office-container-no-backup]). Intake intake.profileData. Row reliability.profile-data.
  10. Profile copies that survive the account ([3, A03.02]): zone-redundant storage for availability (profile.resilience), a vaulted backup for an offsite copy ([3, A03.04], [11, vaulted-survives-source-loss]), and a backup whose last job succeeded, since Microsoft's pages differ on the key access it needs ([12, key-access-needed], [13, keys-or-private], [O1]). Row profile.backup.
  11. Profiles across regions: Cloud Cache rather than storage replication; one pool per user at a time; Azure NetApp Files by its own replication ([3, A03.03], [3, A03.06], [6, cloud-cache-over-storage-replication], [14, ssd-no-geo], [15, zone-and-region-together]). Row profile.cross-region.
  12. Proven by a test: a restore and a failover with a test group, timed against the targets, then a full failover and failback, kept where it survives the outage ([16, RE:09], [16, drills-prove-targets], [6, selective-failover-test], [6, automate-and-align]). The evidence is a run record, not a setting. Row reliability.recovery-test.

Where reliability lives in the family

avd-assess holds this map and method. avd-current-state collects the facts and runs the checks from a pinned copy. avd-landing-zone builds same-tenant recovery: a recovery region, a status check, a configuration snapshot and recovery tests in tiers from rebuild to warm standby, each recovery action a run record (recovery spec); active-active is outside it, and the method still maps it because Microsoft documents it. The evidence each step needs, the draft checks and the facts they wait for are in [G1].

Not yet known

  • The draft checks in [G1] cite facts the register lists as specified; each enters method.json with its facts.
  • Whether the landing zone's default profile backup runs with key access off ([O1]), and whether any tier meets its targets ([O2]).
  • Two Microsoft pages disagree on Azure NetApp Files zone and region replication on one volume ([6, anf-zone-or-region], [15, zone-and-region-together]); the product's own page is read as current.

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]not yet tested files-backup-key-access-off, on files-backup-support#key-access-needed, 2026-10-21. The landing zone keeps storage account key access off on its profile account for the default snapshot-tier backup and turns it on only for the vaulted tier, because two Microsoft pages differ: the support matrix asks for key access, the portal guide accepts key access off when public network access is disabled (ref:files-backup-portal#keys-or-private), which the landing zone does (its recovery spec, facts F14 and F19, open question U1). No real backup job has run with keys off, so whether the default profile backup works at all is unproven. The first landing zone run that reads the last backup job answers it; until then a reviewer treats a key-access-off share with a snapshot policy as unknown, not as backed up.
  2. [O2]not yet tested recovery-tiers-not-yet-tested, on avd-multiregion-bcdr#rto-rpo-by-model, 2026-10-21. The landing zone's same-tenant recovery design (recovery spec, scope and section 4) chooses a tier per landing zone, R0 rebuild, R1 restore anywhere or R2 warm standby (active-passive), and takes its RTO and RPO from Microsoft's estimates; active-active is a non-goal there. Its status check, configuration snapshot and profile recovery test are built and tested offline only: no recovery test has run against a real tenant, so none of the tier targets is measured. The first profile recovery test needs a written estimate and the owner's go; its run record (C17, use case recovery) becomes the evidence that turns this into agrees or disagrees.
