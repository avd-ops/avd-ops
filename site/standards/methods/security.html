Security method

methods/security.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

How to judge an estate's security against what Microsoft publishes for AVD. It is the assessment method applied to the security pillar, with the extra sources security needs. avd-current-state implements it; the findings go in the same report (avd-second-brain contract C21). Nothing here is a security audit or a compliance attestation.

Method

  1. Scope to the customer's half of the shared responsibility table: identity, session host OS, deployment configuration, network controls and app security ([1, shared-responsibility], [G1]).
  2. Start from Microsoft's lists: the review checklist's security items ([2, G02.03], the G items and the rest) and the AVD security guide ([1]), read in the Zero Trust order of identity, endpoints, storage, network, hosts, governance and monitoring ([3, seven-steps]).
  3. Settle the trust boundary first: who shares a host decides between pooled, personal and a separate tenant, and it comes from the operator, not telemetry ([1, trust-boundary], [G2]).
  4. Judge what the control plane shows with Reader only: Trusted launch with Secure Boot and vTPM ([2, G02.03], [O1]), device redirection from the host pool's RDP properties ([4, redirection-properties], [O2]), private endpoints and SMB encryption on the profile share ([2, F01.10], [O3]), diagnostic and audit logging ([2, G03.05]), and Defender for Cloud plans ([2, G03.04]).
  5. Read Defender for Cloud's own results for session hosts where its plan is on, such as a missing EDR or vulnerability findings, and cite them rather than recompute them ([5, vm-recommendations], [G1]). The agents themselves (antivirus, EDR, coexistence, exclusions, network clients on hosts, their cost) are the endpoint protection pillar's rows, agents.* in dimensions.yaml ([G3]).
  6. Judge the host OS against a reviewed baseline profile, Microsoft's baseline for the release minus recorded departures, never against every setting ([6, baselines-published], [7, baselines-in-intune], [G4]).
  7. Leave inside-the-host and directory items unknown until something reads them: local administrators, app control, screen capture protection and watermarking, Conditional Access and MFA ([2, G03.03], [8, host-policy], [9, needs-capture-protection], [2, G04.01], [G1]).
  8. Treat a deliberate trade-off as warn with its reason, and a setting nobody chose as gap; a model never decides which ([O2], [G5]).
  9. Tag each finding twice: the checklist item and pillar for the score, and the security benchmark control for a security reader ([10, ES-1], [G1]).
  10. Repeat on a cadence and compare with the last run, as for every other pillar ([11, milestones]).

Where security lives in the family

Security isn't a separate project. Each foundation repo holds its usual slice, and the upper layers build on them; dependencies point down only, and avd-landing-zone and avd-current-state keep working with nothing above them.

  • avd-assess (this page): what it should be, and why.
  • avd-current-state: what is there now. It collects the security facts and runs these checks from a pinned copy of this method.
  • avd-landing-zone: how it's built. Its defaults should pass these checks, its readiness checks catch drift, and it owns the host baseline profile it builds.
  • avd-second-brain: why it is the way it is over the estate's life, including accepted risks.
  • avd-swarm: how it's operated, with any fix a plan a person approves.

The table and the reasons are in [G1].

Reviewing a deployment

A security reviewer asked to approve deploying AVD with these repos needs a different view: not how to judge an estate, but what the tools themselves do, with which rights, and what proves it. That is the security review map, security-review.yaml (security-review.json, contract C20, avd-assess-security-review/v1). Each claim says in one line what a repo does, links the file at a pinned commit, and carries how strong its evidence is: run (a real run showed it), guarded (a CI check fails if it breaks), built (in the code only) or designed (written down only). It also lists what the operator still owns, the reviewer's questions, a short summary per repo of what it can touch, and the gaps found. It cross-links this method and the pillars rather than restating them, and avd-ops.dev renders it.

Not yet known

  • Four security checks run (method.json version 2); the items that still need a fact, a join or a host-side read are listed in [G6].
  • No host-side collector reads baseline drift, local administrators or app control yet ([G4]).
  • Whether our outcomes agree with Defender for Cloud's for the same estate hasn't been tested ([5, vm-recommendations]).

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]agrees trusted-launch-by-default, on review-checklists-avd#G02.03, 2026-10-20. The landing zone deploys every session host with Trusted launch, Secure Boot and vTPM on, from Gen2 images, and the demo host pool ran on it with no boot or image problem.
  2. [O2]extends redirection-kept-for-usability, on avd-security-guide#device-redirection, 2026-10-20. The landing zone's default RDP properties turn drive, USB and COM port redirection off but keep clipboard, printers, smart cards, WebAuthn and the camera, because users need them. Restricting redirection is a per-property trade-off, so the method reports each one kept on as a warn with its reason, not as a gap.
  3. [O3]extends smb-channel-aes128-gcm-needed, on mcsb-avd-baseline#DP-3, 2026-10-20. Hardening the profile share to AES-256-GCM as the only SMB channel encryption denied every Entra Kerberos session; allowing AES-128-GCM as well, with CCM still off, let users in. Encryption in transit stays on, but the strictest setting isn't usable with Entra Kerberos, so the method treats AES-128-GCM plus AES-256-GCM as passing.
