Targets and benchmarks

methods/targets-benchmarks.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

What good looks like, as numbers with their sources. A benchmark is published (a source states it), prior (a source states it but calls it an estimate) or baseline (no source has a number, so the estate's own measurement sets it).

Method

  1. Round-trip time from the user's network to the host pool's region: under 150 ms (published, [1, rtt-under-150]). Under 100 ms is ideal and over 200 ms is low quality (published, [2, rtt-ideal-100-poor-200], [3, rtt-bands]). Measure it from the user ([O1]).
  2. User input delay: each host ideally under 100 ms (published, [2, input-delay-host-100]); per session, good under 150 ms, acceptable to 500 ms, poor to 2 s (published, [4, input-delay-bands]).
  3. Users per vCPU, multi-session: light 6, medium 4, heavy 2, power 1 (prior, [5, multisession-users-per-vcpu], [5, estimates-only]). Replace it with measurement ([O2]).
  4. Multi-session host size: 6 to 24 vCPUs, never under 4 (published, [5, multisession-vcpu-range]). Our own minimum kit sits at the floor ([O3]).
  5. Profile storage: at least 30 GB per user (prior, [5, profile-storage-minimum]), and the profile storage in the hosts' region ([6, H03.05]).
  6. Logon and time to connect: no published number; set a baseline ([G1], [4, time-to-connect-stages]).
  7. CPU on session hosts: under 50% healthy, over 80% critical, and a queue of two or more per core with high CPU worth investigating (published for Windows generally, not AVD, [7, cpu-bands], [7, pql-per-processor]).
  8. Which number is the reference for each metric, and its standing, is in the gold-standard registry ([G2]).
  9. Reliability and recovery targets are the workload's own, set first ([8, RE:04]).
  10. Before the estate has users, a pilot or scripted load test replaces the users-per-vCPU and size priors for a class; how it is run and where its result goes is ours, because no open workload or pass threshold is published ([G3], [6, C01.10]).
  11. Together, per workload class, these numbers make the baseline profile, with the utilization bands a host should run in ([G4]).

Not yet known

  • No benchmark here has been checked against users we measured; every sizing number is still a prior ([O2]).

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]extends region-latency-from-the-user, on avd-prerequisites#rtt-under-150, 2026-10-20. Latency measured from Cloud Shell says nothing about users, because Cloud Shell runs in an Azure datacenter. Measure round-trip time from the user's device, against endpoints verified to be regional.
  2. [O2]not yet tested users-per-vcpu-adopted, on session-host-sizing#multisession-users-per-vcpu, 2026-10-20. Adopted as the landing zone's automatic sizing input, and its preflight warns above 6 sessions per vCPU. No real users have been measured against it, so the numbers are still Microsoft's prior, not our evidence.
  3. [O3]not yet tested sizing-floor-not-measured, on session-host-sizing#multisession-vcpu-range, 2026-10-20. The landing zone's minimum kit defaults to a 4-vCPU memory-optimized host, which is Microsoft's stated floor and below its 6 to 24 vCPU range, chosen for the smallest test cost. The reasoning that shared hosts run out of memory before CPU is our hypothesis; no measurement backs it yet.
