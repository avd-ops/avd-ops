Entra ID and identity method

methods/entra.md · Edition cfcc302 of avd-assess, 2026-10-27. What changed

How to judge the identity control plane of an Azure Virtual Desktop estate: session host join type, single sign-on, Conditional Access for sign-in, Azure Files Kerberos identity, application group assignments, and administrative role boundaries. It is the assessment method applied to the identity pillar (identity in dimensions.yaml) and the Entra ID control plane (entra). Microsoft documents each identity requirement, so this method links to those sources and adds only the scope page ([G1]): which Microsoft Graph reads and Azure control-plane facts are collected and how they combine with operator intake.

Method

  1. Ask the identity questions the directory and control plane cannot answer before judging the estate: whether Active Directory or Entra Domain Services must stay, which user identity source and join type are intended, where MFA applies, which client devices connect, which sign-in methods are used, and whether external users sign in ([G2], [G1], [1, identity-scenarios]).
  2. Check that each host pool uses one supported session host join type by comparing the Entra join and domain join VM extension counts on its session hosts ([2, one-join-type-per-pool], [3, D03.02], [G1]).
  3. Check single sign-on across both halves of the configuration: the host pool's enablerdsaadauth RDP property in the Azure plane and the Windows Cloud Login service principal and dynamic device group in the Entra plane ([4, host-pool-property], [4, tenant-rdp-enabled], [4, consent-prompt], [3, D03.04], [G1]).
  4. Check Conditional Access policies targeting the AVD service and Windows Cloud Login: require multifactor authentication, align sign-in frequency and session lock behavior, and keep the feed discovery and Azure Windows VM Sign-In apps out of policies that would break passwordless sign-in or feed refresh ([5, target-apps], [5, two-aligned-policies], [5, feed-app-no-mfa], [2, vm-sign-in-app-exclusion], [3, G04.01]).
  5. Check that every enabled AVD Conditional Access policy excludes emergency-access (break-glass) accounts or groups so a conditional-access misconfiguration or provider outage cannot lock administrators out of the tenant ([6, exclude-break-glass], [7, IM-7], [G1]).
  6. Check Azure Files identity-based authentication and its Entra Kerberos service principal: when a profile storage account uses AADKERB, verify that its Entra service principal exists in the directory and is excluded from Conditional Access policies that require interactive MFA ([8, cloud-only-and-hybrid], [8, exclude-from-mfa], [3, D02.01], [G1]).
  7. Check application group assignments and administrative role boundaries: assign Desktop Virtualization User to Entra groups rather than direct users, and separate administrative access with scoped AVD roles below Owner and Contributor ([9, user-role], [9, scoped-roles], [10, groups-not-users], [3, D01.06], [3, G03.06]).
  8. Score Entra checks as not applicable only when the Entra plane is skipped (planesCollected.entra.status != "collected"), and record what stays unknown when a directory read is absent ([G1], [G3]).

Not yet known

  • Whether a Conditional Access policy targeting "All cloud apps" without naming the AVD app IDs satisfies or conflicts with the two-policy baseline on estates that rely on tenant-wide policies ([5, all-apps-conflicts], [G1]).
