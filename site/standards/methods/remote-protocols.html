Remote protocol and session method

methods/remote-protocols.md · Edition a5a7eee of avd-assess, 2026-10-21. What changed

How to judge the way users' sessions reach their hosts: which transport RDP uses and why, what keeps a session alive when a path fails, and the session settings that ride on the transport (redirection, graphics, Teams and media, time limits). It is the assessment method applied to the remote protocol and session pillar (protocol in dimensions.yaml). Almost all of it is documented by Microsoft, so the method links out to those pages and adds only the transport map and the scope page ([G1], [G2]). The networking pillars own how the network provides what RDP needs; this page states what it needs.

Method

  1. Ask how users connect before reading anything: managed networks (ExpressRoute or VPN), public networks, or both, and which clients they run. The intent decides what a good outcome is ([G2], [1, C02.05]).
  2. Read the host pool's switches: the four Shortpath options are Default (enabled), Enabled or Disabled, and UDP over Private Link is a separate opt-in that is off unless set. All of them are readable only through a preview API version, so a GA read leaves them unknown ([2, hostpool-switches], [3, udp-switches-preview-only], [3, private-link-udp-preview-only], [4, udp-opt-in]).
  3. Check the host side where a host read exists: UDP not forced off by policy, and for managed networks the listener and its inbound port ([2, select-transport-policy], [2, listener-for-managed], [2, most-restrictive-wins], [1, F01.11]).
  4. State what RDP needs from the network and hand it to the networking pillars: outbound UDP from hosts, the TURN range on UDP 3478, the client port range, no proxy or inspection as the only path, and several ports per session ([5, proxy-forces-tcp], [6, turn-range], [6, public-network-advice], [2, port-range], [7, ports-per-session]).
  5. Read what each connection used from the logs, through the family's transport map, never one table's vocabulary alone; Insights' connection reliability view shows Multipath too ([G1], [8, transport-type], [7, verify-in-insights], [O1]).
  6. Judge each connection against the intent and the host egress: UDP where expected passes, TURN behind symmetric NAT egress (both landing zone network modes) passes, TURN where a direct path was expected or TCP after UDP was possible is a warn, and UDP turned off with no reason is a gap. TURN doesn't exist in Azure Government. Where UDP fails, point the operator at the NAT type test and the Shortpath error codes ([G2], [6, tcp-first-then-udp], [6, stun-before-turn], [6, symmetric-nat-means-turn], [O2], [2, turn-public-cloud-only], [9, nat-type-test], [9, udp-error-codes]).
  7. Check the clients against the platform table and the Multipath and auto-reconnect floors; the web client never uses Shortpath ([10, shortpath-by-platform], [7, client-floors], [11, needs-multipath]).
  8. Read latency and quality from the network and graphics data: RTT against the published bands, and frame drops by cause. Jitter and loss stay unknown, because no AVD table reports them ([12, rtt-ideal-100-poor-200], [13, rtt-and-bandwidth-only], [14, frame-drops-by-cause]).
  9. Judge QoS and throttling only on managed-network UDP, the one transport that supports them ([15, managed-udp-only], [15, dscp-46], [16, throttle-managed-only]).
  10. Check graphics settings against the hardware: CPU encoding by default, AVC 444 only with hardware encoding, HEVC only on GPU desktops without multimedia redirection ([17, software-default], [18, avc444-needs-hw-encoding], [18, hevc-prerequisites], [19, only-support-verifies]).
  11. Check the session settings that ride on the transport: redirection per kind (new pools start with clipboard, drives, USB and printers off), Teams media optimization and multimedia redirection, disconnected-session time limits and lock behavior ([20, redirection-properties], [21, redirections-off-new-pools], [22, high-level-first], [23, media-optimization], [24, video-playback], [25, disconnected-time-limit], [26, disconnect-on-lock-sso]).
  12. Record what stays unknown and why: no host read, a GA API read, no diagnostic settings, or no operator answer ([G2], [27, diagnostic-tables]).

Not yet known

  • Which log column a real workspace carries ([O1]), and how much round-trip time a TURN relay adds over a direct path, and whether egress firewalls allow it at all ([O2]). One short sandbox run with a client device settles both; it waits on a cost estimate and the owner's go.
  • What share of connections should end up on each transport in a healthy estate. No source publishes one; evidence submissions can ([G3]).
  • No check runs yet. The host pool switches need a C11 fact read through a preview API version, and the per-connection outcome needs C12 facts; both are proposed in dimensions.yaml.

Our observations

What our own runs showed about a cited claim. Evidence links are public and pinned.

  1. [O1]not yet tested transport-column-names-disagree, on configure-rdp-shortpath#verify-transport, 2026-10-21. Two Learn pages query a WVDConnections UdpUse column, while the table reference lists TransportType (Shortpath, TURN, Websocket) and no UdpUse, and Insights uses a third set of values. The family's connection query reads TransportType but hasn't run against a real workspace yet; one sandbox connection settles which column exists. Until then the method maps all three (gap:transport-classification).
  2. [O2]not yet tested symmetric-nat-egress-means-turn, on rdp-shortpath#symmetric-nat-means-turn, 2026-10-21. Both landing zone network modes give hosts symmetric NAT egress, a NAT Gateway when standalone and the hub firewall when hub-peered, so by Microsoft's claim public-network Shortpath should relay through TURN, never connect directly. TURN itself needs outbound UDP 3478 to the relay range; where the egress firewall doesn't allow it, sessions fall back to TCP instead. How much round-trip time the relay adds is unmeasured.
