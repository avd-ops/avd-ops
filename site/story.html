The story behind avd-ops

Six years of looking for a simple, approachable, open way to build Azure Virtual Desktop from the ground up—and keep it running like a well-oiled machine.

From Citrix to cloud VDI

I started out as a Citrix engineer, learning the craft of virtual desktops the hard way: sizing host pools, chasing logon times, tuning storage, and keeping every layer predictable so end users just got a fast, reliable desktop.

I pivoted early to cloud VDI and caught the Windows Virtual Desktop (WVD) wave before it was even renamed Azure Virtual Desktop (AVD). Moving to the cloud solved some old infrastructure headaches, but it brought a new set of challenges across identity, networking, Intune, Microsoft 365, and Azure itself.

Six years searching for a simpler, open path

For the last six years, I kept running into the same gap: it was hard to find a simple, approachable, open solution for building AVD from the ground up—and even harder to find one that stayed useful after day one.

Standing up a host pool once is the easy part. The real work is helping teams adopt the platform, migrate onto it cleanly, and keep it running like a well-oiled machine over time: continuously improving, optimized for cost and performance, and focused on a great user experience.

Where avd-ops started

Built in the open

I started avd-ops in June 2026 as one Azure Virtual Desktop landing zone, built on my own time to see how far a cloud-native deployment could go as readable code.

Every real run that broke something became a lesson and a guard, and those lessons grew into the rest of the ecosystem: read-only estate inventory, an assessment method, migration planning, day-2 operations, optional agents a person approves, and a shared memory of what each deployment taught.

It's still a personal research project: avd-landing-zone and avd-current-state are proven on real deployments, and the rest is being built in the open. None of it is a solo act: it's 100% pair programmed with my buddy Claude.
